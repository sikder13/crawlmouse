# 12 — The crawl worker (CC-12)

> Generated by `pnpm --filter @crawlmouse/worker spec` from `packages/worker/src/spec/render.ts`. Do not edit by hand: `src/spec/spec.test.ts` fails when this file differs from what render.ts renders. Values and tables are read from the code; the sentences around them are written in render.ts, and the tests named beside a rule are what check it.

The worker is a Node 22 HTTP service on Fly (`crawlmouse-worker-staging`). The app sends it signed batches of URLs; it fetches them politely and returns evidence rows. It holds no database key and no Inngest key, and writes nothing anywhere: the caller polls for results. Operations: `docs/ops/worker-runbook.md`.

## Authority

- The HMAC secret is `WORKER_SIGNING_SECRET`, shared with the app. Timestamps are milliseconds, in `x-crawlmouse-ts`; the signature, hex, in `x-crawlmouse-signature`.

- The batch JWT is EdDSA (Ed25519). The worker holds only the public key (`WORKER_JWT_PUBLIC_KEY`, base64url), so it cannot mint one. Audience `crawlmouse-worker`, role `crawl_worker`; claims `check_id`, `site_id`, `site_host`, `batch`, `nonce`, `iat`, `exp`, and no others.

- The batch must name the same check, site, batch and nonce as its JWT, and every URL must be on `site_host`, with or without `www.`. Anything else is `jwt_scope`.

## Politeness

- Request starts at least 500 ms apart per registrable domain (eTLD+1, Public Suffix List with its private section), shared by every batch in the process, measured start to start.

- One request in flight per site; two when the median latency of the last 20 responses is over 500 ms and no Crawl-delay raised the gap.

- Crawl-delay: the largest that applies to any identity the batch sends, honoured in full up to 30 s. From 10 s the batch is partial (`crawl_delay_10s_or_more`) with its coverage; above 30 s nothing but robots.txt is requested (`crawl_delay_over_limit`).

- A site is stopped for 10 min after 3 responses of 429, or 4 consecutive challenged pages (in a crawl batch, a challenged fetch; in an access batch, a challenged control). A batch records a stop it met or caused as a finding; it is partial with `site_stopped` only when the stop refused one of its requests.

- Redirects are followed one paced request at a time. A redirect to another registrable domain is recorded, not requested; robots.txt redirects are followed, as RFC 9309 asks.

## robots.txt

- Our requests obey the `Crawlmouse` and `CrawlmouseBot` groups (every one present must allow), else `*`. A crawler's request also obeys its own group, else `*`. A path a group forbids is not requested under it, and neither is a redirect target it forbids.

- Before any page, the batch reads robots.txt origin by origin in the order of its URLs (www and bare, either scheme) and stops at the first origin that blocks the site. A redirect chain of more than five hops on robots.txt is read as unreachable. A 4xx means no robots.txt: everything is allowed. A 5xx, a timeout, a network error, a challenge, or a file cut off by what the byte budget had left means robots.txt is unreachable.

- A file larger than 500 KiB (UTF-8 bytes after any byte order mark, as the engine's parser counts them), or one with more than 5000 rules in a group for a user agent the worker reads, is too large to evaluate. The groups are counted one at a time: a file whose `*` and Googlebot groups each hold 5000 rules is read (`src/politeness/robots.test.ts`, "too large to evaluate").

- If an origin of the batch's URLs is unreachable, too large to evaluate, refused by the SSRF guard, or asks for a Crawl-delay over the limit, no page of the batch is requested: an access batch's rows are `not_measured` with the reason, never `disallowed_by_robots`, and a crawl batch's pages are `not_requested` with it (`src/batch/run.test.ts`, "robots.txt unreachable" and "robots.txt too large to evaluate").

- An origin first reached by a redirect has its robots.txt read when the redirect needs it. If that origin fails the same way, the redirect is not followed, its page says why, and the batch is partial with the reason (`src/batch/run.test.ts`, "a redirect to an origin whose robots.txt cannot be read").

- A redirect to another origin of the site is followed only after that origin's robots.txt is read, and a batch reads robots.txt for at most 8 origins; a redirect to one more is recorded, not requested. A redirect to a URL that is not http or https is recorded, not requested.

- A 200 whose body starts with a tag is a soft 404: no robots.txt. The body decides, not the Content-Type, so rules served as text/html are read.

## The page reader thread

- Pages are parsed for their text, word count and links on one thread of the process's own (`src/reader/`), so the event loop that times requests never waits on a parse. Bodies go to it as UTF-8 bytes in a transferred buffer, and it answers in the order asked.

- If the thread dies (out of memory, say), the batch it was reading for stops: that page is fetched but not read, no request of the batch starts after it (its pages not yet requested are `not_requested`), and the batch is partial with `reader_thread_crashed`. The next read starts a new thread (`src/reader/thread-reader.test.ts`, `src/batch/run.test.ts`, "the page reader thread dies").

## Reading a response

In this order, first match wins: no response is `error`; a challenge (below) is `challenged`; a final URL on another registrable domain is `redirected_away`; then by status: 2xx `served`, 402 `payment`, 429 `rate_limited`, 404 and 410 `gone`, other 4xx and 999 `refused`, anything else `error`.

A challenge is recognised from, in order:

| Evidence                                          | Matches                                                                                                                                     |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Mitigation header                                 | `cf-mitigated` containing `challenge`; `x-vercel-mitigated` containing `challenge`                                                          |
| Redirect to a challenge endpoint                  | `/cdn-cgi/challenge-platform/`, `captcha-delivery.com/`, `/_incapsula_resource`, `/.well-known/sgcaptcha`, `/_sec/cp_challenge`             |
| Body, only on a 403 or 503, first 8192 characters | `just a moment...`, `/cdn-cgi/challenge-platform/`, `captcha-delivery.com`, `px-captcha`, `incapsula incident id`, `/.well-known/sgcaptcha` |

## The decision table

A refusal is `blocked_by_ua_rule` only when the tagged Googlebot canary was served on that page; otherwise `refused_unverified`, with the crawlers served on the page named in the row's limitations. The canary is requested on a page only when a crawler was refused there and robots.txt allows Googlebot. Thin is under 80% of the control's words.

## Evidence on a row

Rows are `AccessTest` (CC-11) for access batches, `CrawlPage` and `LinkEdge` for crawl batches, validated against their schemas before they leave the worker. Each carries `source_ip_class: fly_egress`, the identity sent, the request headers, these response headers only: `server`, `content-type`, `location`, `retry-after`, `cf-mitigated`, `x-vercel-mitigated`, `cf-ray`, `crawler-price`, byte and word counts, the final URL, and `limitations[]`.

A batch result is `partial` when any of these held: `budget_requests`, `budget_bytes`, `budget_seconds`, `site_stopped`, `robots_unreachable`, `robots_too_large`, `site_refused`, `crawl_delay_over_limit`, `crawl_delay_10s_or_more`, `result_size`, `reader_thread_crashed`. `coverage` gives the URLs requested and the URLs complete: in an access batch, a page where every tested crawler's verdict is other than `not_measured`; in a crawl batch, a page that got a response, other than a redirect the batch stopped before following, or a page robots.txt disallows.

## What this evidence cannot show

- Requests come from Crawlmouse's egress address, not the operators'. A site that verifies crawler IPs treats them as unverified; `challenged_ua` and `refused_unverified` say the real crawler may pass.

- The tag is appended to each crawler's user agent, so a rule matching the exact string does not fire on it, and a block can be under-reported.

- No JavaScript runs. Text and links are those in the HTML as served (rendering is CC-14).
