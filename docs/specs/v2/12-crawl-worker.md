# 12 — The crawl worker (CC-12)

> Generated by `pnpm --filter @crawlmouse/worker spec` from `packages/worker/src/spec/render.ts`. Do not edit by hand: `src/spec/spec.test.ts` fails when this file differs from what render.ts renders. Values and tables are read from the code; the sentences around them are written in render.ts, and the tests named beside a rule are what check it.

The worker is a Node 22 HTTP service on Fly (`crawlmouse-worker-staging`). The app sends it signed batches of URLs; it fetches them politely and returns evidence rows. It holds no database key and no Inngest key, and writes nothing anywhere: the caller polls for results. Operations: `docs/ops/worker-runbook.md`.

## Authority

- The HMAC secret is `WORKER_SIGNING_SECRET`, shared with the app. Timestamps are milliseconds, in `x-crawlmouse-ts`; the signature, hex, in `x-crawlmouse-signature`.

- The batch JWT is EdDSA (Ed25519). The worker holds only the public key (`WORKER_JWT_PUBLIC_KEY`, base64url), so it cannot mint one. Audience `crawlmouse-worker`, role `crawl_worker`; claims `check_id`, `site_id`, `site_host`, `batch`, `nonce`, `iat`, `exp`, and no others.

- The batch must name the same check, site, batch and nonce as its JWT, and every URL must be on `site_host`, with or without `www.`. Anything else is `jwt_scope`.

## Politeness

- Request starts at least 500 ms apart per registrable domain (eTLD+1, Public Suffix List with its private section), shared by every batch in the process, measured start to start.

- One request in flight per site; two when the median latency of the last 20 responses is over 500 ms and no Crawl-delay raised the gap.

- Crawl-delay: the largest that applies to any identity the batch sends, honoured in full up to 30 s. From 10 s the batch is partial (`crawl_delay_10s_or_more`) with its coverage; above 30 s nothing but robots.txt is requested (`crawl_delay_over_limit`).

- A site is stopped for 10 min after 3 responses of 429, or 4 consecutive challenged pages (in a crawl batch, a challenged fetch; in an access batch, a challenged control). A batch records a stop it met or caused as a finding; it is partial with `site_stopped` only when the stop refused one of its requests.

- Redirects are followed one paced request at a time. A redirect to another registrable domain is recorded, not requested; robots.txt redirects are followed, as RFC 9309 asks.

## robots.txt

- Our requests obey the `Crawlmouse` and `CrawlmouseBot` groups (every one present must allow), else `*`. A crawler's request also obeys its own group, else `*`. A path a group forbids is not requested under it, and neither is a redirect target it forbids.

- Before any page, the batch reads robots.txt origin by origin in the order of its URLs (www and bare, either scheme) and stops at the first origin that blocks the site. A redirect chain of more than five hops on robots.txt is read as unreachable. A 4xx means no robots.txt: everything is allowed. A 5xx, a timeout, a network error, a challenge, or a file cut off by what the byte budget had left means robots.txt is unreachable.

- A file larger than 500 KiB (UTF-8 bytes after any byte order mark, as the engine's parser counts them), or one with more than 5000 rules in a group for a user agent the worker reads, is too large to evaluate. The groups are counted one at a time: a file whose `*` and Googlebot groups each hold 5000 rules is read (`src/politeness/robots.test.ts`, "too large to evaluate").

- If an origin of the batch's URLs is unreachable, too large to evaluate, refused by the SSRF guard, or asks for a Crawl-delay over the limit, no page of the batch is requested: an access batch's rows are `not_measured` with the reason, never `disallowed_by_robots`, and a crawl batch's pages are `not_requested` with it (`src/batch/run.test.ts`, "robots.txt unreachable" and "robots.txt too large to evaluate").

- An origin first reached by a redirect has its robots.txt read when the redirect needs it. If that origin fails the same way, the redirect is not followed, its page says why, and the batch is partial with the reason (`src/batch/run.test.ts`, "a redirect to an origin whose robots.txt cannot be read").

- A redirect to another origin of the site is followed only after that origin's robots.txt is read, and a batch reads robots.txt for at most 8 origins; a redirect to one more is recorded, not requested. A redirect to a URL that is not http or https is recorded, not requested.

- A 200 whose body starts with a tag is a soft 404: no robots.txt. The body decides, not the Content-Type, so rules served as text/html are read.

## The page reader thread

- Pages are parsed for their text, word count and links on one thread of the process's own (`src/reader/`), so the event loop that times requests never waits on a parse. Bodies go to it as UTF-8 bytes in a transferred buffer, and it answers in the order asked.

- A page that nests elements more than 512 deep is parsed only to that depth, then the parse stops: the page is fetched and not read, with the reason `parse_depth_exceeded` (`src/rows/text.test.ts`, `src/reader/hostile-page.test.ts`).

- A read the thread is still on 20 s after reaching it fails with `reader_deadline`: the thread is stopped and a new one started. If the thread dies (out of memory, say), the read it was on fails with `reader_thread_crashed`. Either way the reads queued behind it go to the new thread, in order. A read that throws fails with `reader_error`, and the thread goes on (`src/reader/thread-reader.test.ts`).

- A response not read for any of these reasons fails alone: a crawl page is fetched and not complete, an access row is `not_measured`, the batch goes on, and none of them is a fault of the site or makes the batch partial. The result's findings count them by reason as `not_read` (`src/batch/run.test.ts`, "a page the reader gives no answer for fails alone").

## A page with no `<body>`

htmlparser2, the worker's parser, builds no element a page does not write, so a page with no `<body>` tag has no body element. Its main content (`content_simhash`) and its served text (`raw_text`, its word count, and the words the access comparison counts) are read from the body its HTML implies, as a browser's parser builds it: the engine's `ImpliedBody`, which `MainContentWalk` reads with `impliedBody: true`.

- From the start of the document, these stay out of the body: text of HTML whitespace only (U+0020, U+0009, U+000A, U+000C, U+000D; a no-break space is not whitespace), comments and the doctype; `<html>`, `<head>`, whose contents are read in turn; `<base>`, `<basefont>`, `<bgsound>`, `<link>`, `<meta>`, which the parser closes at once, so what htmlparser2 nests in one follows it; and `<title>`, `<noframes>`, `<noscript>`, `<script>`, `<style>`, `<template>`, with what is inside them. `<noscript>` stays in the head only until a `<head>` element has closed; after that, the body starts at it.

- The first other node starts the body: text that is not whitespace only, or another element. It and the nodes after it are body content. A later `<head>` or `<html>` tag only wraps body content, as the parser ignores those tags there.

- A `<frameset>` before the body starts leaves the page no body: no main content and no served text. After the body starts, a `<frameset>` replaces it while the frameset-ok flag holds. The flag clears on text that is not whitespace only, or on `<pre>`, `<listing>`, `<li>`, `<dd>`, `<dt>`, `<button>`, `<applet>`, `<marquee>`, `<object>`, `<table>`, `<area>`, `<br>`, `<embed>`, `<img>`, `<image>`, `<keygen>`, `<wbr>`, `<input>`, `<hr>`, `<textarea>`, `<xmp>`, `<iframe>`, `<select>` (an `<input>` only when its type is not `hidden`), read in the body or inside a `<template>` and outside `<script>`, `<style>`, `<title>`, `<textarea>`, `<xmp>`, `<iframe>`, `<noembed>`, `<noframes>`, `<noscript>`. A `<template>` start clears it too, in the head as in the body.

- A page with a `<body>` element reads as before: its main content from the first one in document order, and its served text from the one at the top of the document or under its `<html>`, or from the whole document when there is one only lower down.

- Tests: `packages/engine/src/analysis/ai-readiness/main-content-walk-implied-body.test.ts`, which pins these cases against parse5, and `src/reader/bodyless.test.ts`, on a page shaped like info.cern.ch's.

- Known gap: htmlparser2 builds a `<body>` inside `<noframes>`, which a browser reads as text. Such a page has a body element, so it is read from that body, as before (`packages/engine/fixtures/v2/main-content/noframes-body.html`).

- Known gap: the rule reads htmlparser2's tree, which does not hold everything the browser's parser decides on. A stray `</html>` or `</body>`, which htmlparser2 drops, starts the body in a browser; a `</head>` with no `<head>` element closes the browser's implied head; a stray `</p>`, an element to htmlparser2, is ignored before the body by a browser; and inside `<svg>` a browser reads `<title>` and `<frameset>` by other rules. These six are pinned, with what parse5 reads instead, under "known gaps" in the engine test above. Other elements inside `<svg>` or `<math>` may differ the same way; they are not measured.

## Reading a response

In this order, first match wins: no response is `error`; a challenge (below) is `challenged`; a final URL on another registrable domain is `redirected_away`; then by status: 2xx `served`, 402 `payment`, 429 `rate_limited`, 404 and 410 `gone`, other 4xx and 999 `refused`, anything else `error`.

A challenge is recognised from, in order:

| Evidence                                          | Matches                                                                                                                                     |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Mitigation header                                 | `cf-mitigated` containing `challenge`; `x-vercel-mitigated` containing `challenge`                                                          |
| Redirect to a challenge endpoint                  | `/cdn-cgi/challenge-platform/`, `captcha-delivery.com/`, `/_incapsula_resource`, `/.well-known/sgcaptcha`, `/_sec/cp_challenge`             |
| Body, only on a 403 or 503, first 8192 characters | `just a moment...`, `/cdn-cgi/challenge-platform/`, `captcha-delivery.com`, `px-captcha`, `incapsula incident id`, `/.well-known/sgcaptcha` |

## The decision table

One verdict per tested crawler per sampled page. Rows are evaluated top to bottom; the first whose conditions all hold wins. A refusal is `blocked_by_ua_rule` when another tested crawler or the tagged Googlebot canary was served on that page (the witness rule, ENGINE-GAP §3.5a), and the first served, in request order, is the row's `witness`; the browser control is not a witness. Otherwise it is `refused_unverified`: nothing else we sent that claims to be a crawler was served on the page. The canary is requested on a page only when a crawler was refused there and robots.txt allows Googlebot. Thin is under 80% of the control's words.

## Evidence on a row

Rows are `AccessTest` (CC-11) for access batches, `CrawlPage` and `LinkEdge` for crawl batches, validated against their schemas before they leave the worker. Each carries the identity sent, the request headers, these response headers only: `server`, `content-type`, `location`, `retry-after`, `cf-mitigated`, `x-vercel-mitigated`, `cf-ray`, `crawler-price`, `x-vercel-id`, `x-amz-cf-id`, `via`, `akamai-grn`, `akamai-cache-status`, `x-sucuri-id`, `x-sucuri-cache`, byte and word counts, the final URL, `limitations[]`, and the vantage below.

Where the CDN and proxy headers come from, each from its vendor: `x-vercel-id`, [Vercel](https://vercel.com/docs/headers/response-headers); `x-amz-cf-id`, [Amazon CloudFront](https://aws.amazon.com/developer/application-security-performance/articles/troubleshooting); `via`, [RFC 9110 §7.6.3](https://www.rfc-editor.org/rfc/rfc9110#section-7.6.3); `akamai-grn` and `akamai-cache-status`, the default names of two headers an Akamai property can turn on ([Global Request Number](https://techdocs.akamai.com/terraform/docs/global-request-number), [Return Cache Status](https://techdocs.akamai.com/terraform/docs/return-cache-status)), so a property may send them under other names or not at all; `x-sucuri-id` and `x-sucuri-cache`, [Sucuri](https://docs.sucuri.net/website-firewall/troubleshooting/investigating-cache-headers/). Each value is cut like every header value.

## Declaration files

In each crawl batch, after its pages and after the batch's own accounting, the worker requests each of `/llms.txt`, `/llms-full.txt`, `/.well-known/ucp`, `/.well-known/mcp`, `/.well-known/agent-card.json`, `/rsl.xml`, `/sitemap.xml` on the origin of the batch's first URL, as our crawler, through the site's limiter and the batch's budget like any request (`/robots.txt` is read already). Each is recorded as `DeclarationFetch` (`packages/types/src/v2/declaration.ts`): status, media type (the Content-Type as sent, cut to its budget) and the decoded bytes read, never the body. Reading stops once more than 65536 bytes of the body have arrived (the chunk that crosses it is counted), and `bytes_complete` is then false; a redirect is recorded as it answered and not followed; a path robots.txt disallows us is `not_requested: robots_disallowed`, and the others not requested say why (`budget`, `site_stopped`, `site_blocked`). A 429 to a declaration does not count towards stopping the site, so a path a site rate-limits on its own cannot stop the crawl of its pages; what became of each is on its own record only, and a declaration does not change the batch's coverage, findings or partial reasons. What an origin answered is kept (`DeclarationCache`): a file's answer for ten minutes, as robots.txt is; a transient one (408, 425, 429 or a 5xx) for its Retry-After, at least a minute and at most ten. A later batch carries kept records with `from_cache: true` instead of asking again, and asks again for any that got no answer. A site that answers every declaration with 429 is therefore asked at most once a minute per path, and those 429s do not count towards stopping the site. An access batch requests none. Tests: `src/batch/declarations.test.ts`.

A batch result is `partial` when any of these held, the contract's `BatchPartialReason` values: `budget_requests`, `budget_bytes`, `budget_seconds`, `site_stopped`, `robots_unreachable`, `robots_too_large`, `site_refused`, `crawl_delay_over_limit`, `crawl_delay_10s_or_more`, `result_size`. `coverage` gives the URLs requested and the URLs complete: in an access batch, a page where every tested crawler's verdict is other than `not_measured`; in a crawl batch, a page that got a response, other than a redirect the batch stopped before following or an HTML page that was not read, or a page robots.txt disallows.

## What this evidence cannot show

- Requests come from Crawlmouse's egress address, not the operators'. A site that verifies crawler IPs treats them as unverified; `challenged_ua` and `refused_unverified` say the real crawler may pass.

- The tag is appended to each crawler's user agent, so a rule matching the exact string does not fire on it, and a block can be under-reported.

- No JavaScript runs. Text and links are those in the HTML as served (rendering is CC-14).
