- `engine_sha`: the git commit the engine was built from. Check: `grep -rn "engine_sha\|GIT_SHA\|FLY_IMAGE_REF" packages/engine/src packages/worker/src`.
- `detector_ruleset_version`: a semver the engine bumps when the verdict table, a detector threshold or a signature changes. Check: `grep -rni "ruleset_version\|detector_version" packages/engine/src packages/worker/src`.

Verify: `pnpm --filter @crawlmouse/types exec vitest run src/v2/measurement.test.ts -t crawlerRegistryVersion`.
- `worker_release`: the worker build that fetched (an image reference). The worker does not report one yet. Check: `grep -rn "FLY_IMAGE_REF\|version" packages/worker/src/server.ts`.

The database checks these values’ shape, not their meaning: `worker_release` accepts any printable text up to 200 characters, an account id included. What fills it is the writer’s rule (an image reference, one lineage per build), set by the follow-up that produces these values (§9).

## 3. Measurement status

Every scored measurement carries one of `measured`, `not_measurable`, `unevaluable`, `withheld` (the contract's `MeasurementStatus`): **measured**, observed and asserted; **not measurable**, we tried and the site or our method prevented the observation; **unevaluable**, no usable observation exists to decide from; **withheld**, observed and declined because the evidence cannot support a value. It generalises SPEC 5.1a's refusal: a refused grade is withheld.

**`measured` is not "fully measured".** A Technical SEO grade whose `refusal.unevaluable` lists triggers is measured: the letter is shown. The triggers it could not evaluate stay on the record, in the grade’s `refusal` (SPEC 5.1a’s fields), and a reader of the status reads them there. Verify: `pnpm --filter @crawlmouse/types exec vitest run src/v2/measurement.test.ts -t "unevaluable refusal triggers"`.

The mapping, rendered by running the contract’s functions (`packages/types/src/v2/measurement.ts`) over every value they take. The database computes the same values in generated columns, so no writer can store a status of its own; and the two values the statuses read, `technical_seo.refusal.refused` and `ai_readability.withheld`, must be booleans (`checks_technical_seo_refused`, `checks_ai_readability_withheld`), so SQL and the functions read every stored grade alike. ## 4. Monthly partitions

| Table                           | Partition key            |
| ------------------------------- | ------------------------ |
| `access_tests`                  | `RANGE (check_month)`    |
| `link_edges`                    | `RANGE (check_month)`    |
| `page_results`                  | `RANGE (check_month)`    |
| `research.check_runs`           | `RANGE (observed_month)` |
| `research.crawler_observations` | `RANGE (observed_month)` |

Read from `pg_partitioned_table`. ARCH-2 §9 deferred partitioning `page_results` to about 3,000 accounts, on a copied `finished_month`. Here it is from creation, so retention can be a partition drop, and the key is `checks.check_month` (the UTC month the check was queued, a generated column), because a check’s rows are written while `finished_at` is still null.

- **One check, one partition.** The foreign key `(check_id, check_month)` to `checks (id, check_month)` keeps every row of a check in its queued month’s partition, so a drop never splits a check, and a row with another month is refused. The keys of the three tables include `check_month`, as a partitioned table’s unique keys must; a writer’s `on conflict` names it.
- **Where partitions live.** In the schema `partitions`, which no client role, `service_role` included, may use; each with RLS on and every role’s privileges revoked. On production a new table in `public` would arrive with every privilege for `anon` and `authenticated` (`pg_default_acl`); a partition there would be a second, ungated copy of its rows. Rows are read and written through the parent, whose grants and policies apply. Verify: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-006b-data-foundations.test.ts -t "monthly partitions"`.
- **What creates them.** `public.v2_premake_month_partitions(from, through)`, `service_role` only, creates each missing month from the month of `from` to the month of `through` (inclusive, at most 37 months) for every table in `public` or `research` range-partitioned on one `date` column named `check_month` or `observed_month`. It finds them in the catalog, so a table partitioned later is covered without editing it, and it returns how many it created (0 on a re-run). Postgres clones a parent’s row triggers onto a new partition but not its statement triggers, so the function creates each of the parent’s TRUNCATE triggers (the ledger’s) on the partition. 003 and 006b each call it for the month they run in and the three after it. The owner’s daily `pg_cron` job (runbook) keeps it three months ahead; that is the primary mechanism.
- **`pg_partman`** is available on Supabase (`supabase.com/docs/guides/database/extensions/pg_partman`: enabled into its own schema, maintained by a scheduled `run_maintenance_proc`). It is not used: PGlite, which the tests run on, does not have it, and the function above is tested. The owner verifies its availability on the project before ever relying on it.
- **No default partition.** A row for a month with no partition is refused, not filed somewhere a drop would miss; a default partition would also make every later month’s creation scan it. If the cron job stops, writes fail loudly once the three premade months run out.
- **Earlier months.** 004’s backfill writes migrated audits’ pages into their own months, so it calls the function for those months first.

### What the ledger may hold

Exactly these columns, with these types; anything else in the schema fails the guard. It also reads the ledger’s partitions, foreign keys, functions, triggers, rules and the functions its CHECKs, policies and defaults call, the columns of `measurement_lineages` (the one table it may reference, pinned like the ledger, with no reference of its own), anything in `partitions` that is no partition or partition index of a table in `public` or `research`, and any relation in `research` that is not a table or index (a sequence, a view, a composite type). Two rules underlie it, read from `pg_depend`: nothing outside the ledger depends on it but the link table’s key, and the ledger’s own objects depend on nothing outside it but its two schemas, its functions (each pinned by the md5 of its definition), `measurement_lineages` and that key. ### The site key

`site_key` is HMAC-SHA256 of the registrable domain (eTLD+1, lowercased), as 64 hex characters, under the key `RESEARCH_SITE_KEY`. The key is a server-side secret: the owner generates it, it is set in the server environment only, and it is never stored in the database, so the ledger alone cannot be reversed to a domain by trying candidate domains. It is not listed in `turbo.json` `build.env`, because nothing reads it at build time; it is added there only if a build-time read is ever needed. `site_key_version` names the key: a rotation (only after a compromise, since it breaks the series) writes new rows under the next version.

### What de-identification here does not cover

- The guard reads the catalog, and a function whose body is a string (plpgsql, or SQL written between quotes) records no dependency on what its body names. A ledger function’s body is held by its md5 pin. A function anywhere else whose body reads the ledger is seen only when its signature names a ledger row type (an inbound dependency); one that names the ledger only inside its body, statically or in dynamic SQL, is not. Migrations are owner-applied and reviewed (OPERATING-RULES §7); that review is the control for it, and the guard is its aid, not its replacement. Verify the case it does see: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-006b-data-foundations.test.ts -t "returns ledger rows"`.
- While a link exists, `service_role` can join a check to its runs: that is the link’s purpose.
- A run’s quasi-identifiers (CMS, framework, edge vendor, robots rules per crawler) can narrow it to a few candidate sites for anyone who holds the ledger; with `RESEARCH_SITE_KEY` as well, a candidate can be confirmed. The key’s secrecy is the control.
- Rows written in the same transaction as a check’s finalize share its transaction id (`xmin`) while both rows exist. The writer inserts ledger rows in a transaction of their own (follow-up), and the export never carries system columns.
- A run names its lineage, and any signed-in user can read a lineage’s `created_at`, so a run is known to be later than that instant. A lineage is shared by every run of its builds, so this bounds a run by a deploy, not by a check.

## 7. Usage metering

One `usage_events` row per delivered result: a finished check, an export, later an API call. Written by the server. Account-scoped: an audit nobody kept is not metered here, and anonymous volume is counted in PostHog.

- **Members read counts only.** No client role reads a row. `public.usage_counts(account)`, executable by `authenticated`, returns the account’s events counted by UTC month, kind, result and billable, for a member of that account, and nothing for anyone else, decided before a row is read. Membership is the caller’s seat, so a caller with no signed-in user (`service_role` included) gets nothing; the server reads `usage_events` directly.

- `result`: `delivered` when at least one grade (or the export, or the API answer) was given; `withheld` when everything asked for was withheld; `refused` when the request was refused before work (a cap, the opt-out registry, a plan gate); `failed` when the work failed. Only `delivered` can be `billable` (`usage_events_billable`).
- A check, report or key named must be the event’s account’s (`usage_events_references`). The row is append-only, except the clearing of a reference whose row was deleted and the cascade of its account.
- A scoped seat reads its whole account’s counts: metering is account-level, and a count names no site.

Verify: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-006b-data-foundations.test.ts -t "usage_events"`.

## 8. Where this differs from the design documents and the code

- **ARCH-2 §9** partitions `page_results` later, on a copied `finished_month`; here, from creation, on `checks.check_month` (§4).
- **ARCH-2 §2.6/§2.7 retention** is count-based (12 checks per site for `page_results`, two for `link_edges`), which month drops cannot express; the owner ruled 13 months on every plan for per-page rows and kept the two-check rule for `link_edges` (§5).
- **"The plan-driven expiry the contract already has"** does not exist: the contract has `Check.expires_at`, for anonymous checks only. No expiry column was added (§5).
- **`access_tests`** is not in ARCH-2; its retention follows `page_results` (owner ruling).
- **The `crawl_worker` token** gains a `lineage_id` claim; the minting step (docs/specs/v2/06-check-tables.md) sets it.
- **The contract gains only what stands on its own:** the entities `MeasurementLineage` and `UsageEvent` (with their fixture collections `lineages` and `usage_events`), the enums `MeasurementStatus` (a derived enum: every value comes out of the status functions over the fixtures), `UsageKind` and `UsageResult`, the status functions, and `crawlerRegistryVersion`. Rendered in `docs/specs/v2/11-type-contract.md`.
- **Database only, against the approved plan.** The plan put `lineage_id`, the statuses and the vantage fields on the contract's `Check`, `PageResult`, `LinkEdge` and `AccessTest`. A required field there fails the engine's diff fixtures (`packages/engine/fixtures/v2/diff/builders.ts` builds a `Check`) and the worker's rows, which the worker parses with the contract's schemas (`grep -rln "AccessTestSchema\|LinkEdgeSchema" packages/worker/src`); both packages are outside this step, which changes no worker or pipeline code. So these are database-only columns here, listed in 06's "Database-only columns", and the step that next changes the engine and the worker adds them to the contract. `check_month`, `usage_events.api_key_id` and `usage_events.idempotency_key` are database only by design. The ledger is not in the contract: no screen or API reads it.

-- SECURITY INVOKER, so current_user is the role that wrote. research_retention may delete; nothing
-- may update or truncate, the table owner included. The TRUNCATE trigger is a statement trigger,
-- which Postgres does not clone onto partitions; v2_premake_month_partitions creates it on each.

create or replace function research.ledger_append_only()
returns trigger
language plpgsql
set search_path = pg_catalog
as $$
begin
  if tg_op = 'DELETE' and current_user = 'research_retention' then
    return old;
  end if;
  raise exception 'research.%: the ledger is append-only; a correction is a new row that supersedes it',
    tg_table_name using errcode = '55000';
end;
$$;

-- A run supersedes a run of the same site, under the same site key version. A half-set pair is
-- check_runs_supersedes_pair's to refuse.
create or replace function research.check_runs_supersedes_same_site()
returns trigger
language plpgsql
set search_path = pg_catalog
as $$
begin
  if new.supersedes_id is not null and new.supersedes_month is not null and not exists (
       select 1 from research.check_runs r
        where r.id = new.supersedes_id and r.observed_month = new.supersedes_month
          and r.site_key = new.site_key and r.site_key_version = new.site_key_version) then
    raise exception 'research.check_runs: a run supersedes a run of the same site' using errcode = '23503';
  end if;
  return new;
end;
$$;

-- An event's check, report and key belong to its account. Checked when the row is written.
create or replace function public.usage_events_references()
returns trigger
language plpgsql
security definer
set search_path = pg_catalog, public
as $$
begin
  if new.check_id is not null and not exists (
       select 1 from public.checks c join public.sites s on s.id = c.site_id
        where c.id = new.check_id and s.account_id = new.account_id) then
    raise exception 'usage_events: check_id must be a check of the event''s account' using errcode = '23503';
  end if;
  if new.report_id is not null and not exists (
       select 1 from public.reports r where r.id = new.report_id and r.account_id = new.account_id) then
    raise exception 'usage_events: report_id must be a report of the event''s account' using errcode = '23503';
  end if;
  if new.api_key_id is not null and not exists (
       select 1 from public.api_keys k where k.id = new.api_key_id and k.account_id = new.account_id) then
    raise exception 'usage_events: api_key_id must be a key of the event''s account' using errcode = '23503';
  end if;
  return new;
end;
$$;

-- Refuses UPDATE, DELETE and TRUNCATE whoever writes. Let through, as fix_events_append_only does: the
-- delete of an event whose account no longer exists, and an update that clears check_id, report_id or
-- api_key_id once the row it named no longer exists (their foreign keys' set null) and changes
-- nothing else.
create or replace function public.usage_events_append_only()
returns trigger
language plpgsql
security definer
set search_path = pg_catalog, public
as $$
begin
  if tg_op = 'DELETE' then
    if not exists (select 1 from public.accounts a where a.id = old.account_id) then
      return old;
    end if;
  elsif tg_op = 'UPDATE' then
    if (new.id, new.account_id, new.kind, new.result, new.billable, new.compute_seconds,
        new.request_count, new.occurred_at, new.idempotency_key)
         is not distinct from
       (old.id, old.account_id, old.kind, old.result, old.billable, old.compute_seconds,
        old.request_count, old.occurred_at, old.idempotency_key)
       and (new.check_id is not distinct from old.check_id
            or (new.check_id is null and not exists (select 1 from public.checks c where c.id = old.check_id)))
       and (new.report_id is not distinct from old.report_id
            or (new.report_id is null and not exists (select 1 from public.reports r where r.id = old.report_id)))
       and (new.api_key_id is not distinct from old.api_key_id
            or (new.api_key_id is null and not exists (select 1 from public.api_keys k where k.id = old.api_key_id)))
       and (new.check_id, new.report_id, new.api_key_id)
           is distinct from (old.check_id, old.report_id, old.api_key_id)
    then
      return new;
    end if;
  end if;
  raise exception 'usage_events is append-only' using errcode = '55000';
end;
$$;

revoke all on function public.usage_events_references() from public, anon, authenticated, service_role;
revoke all on function public.usage_events_append_only() from public, anon, authenticated, service_role;

-- The account's events counted by UTC month, kind, result and billable, for a member of the account;
-- nothing for anyone else, decided before a row is read. Membership is the caller's seat
-- (auth.uid()), so a caller with no signed-in user, service_role included, gets nothing; the server
-- reads usage_events directly. SECURITY DEFINER because no client role reads usage_events.
create or replace function public.usage_counts(p_account uuid)
returns table (month date, kind text, result text, billable boolean, events bigint)
language plpgsql
stable
security definer
set search_path = pg_catalog, public
as $$
begin
  if not coalesce(public.is_member(p_account), false) then
    return;
  end if;
  return query
    select date_trunc('month', u.occurred_at at time zone 'UTC')::date, u.kind, u.result, u.billable,
           count(*)
      from public.usage_events u
     where u.account_id = p_account
     group by 1, 2, 3, 4
     order by 1, 2, 3, 4;
end;
$$;

revoke all on function public.usage_counts(uuid) from public, anon, authenticated;
grant execute on function public.usage_counts(uuid) to authenticated, service_role;
