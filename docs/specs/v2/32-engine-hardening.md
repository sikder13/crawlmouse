# SPEC 32 — Engine hardening (CC-32)

The engine says only what it measured, and the fetch guard has no gap, before v2 is switched on. Each
section gives the decision, the answers the build acted on (`questions.md` in the step's notes, with
the owner's rulings), and the gaps it leaves. The generated specs named below say what the code does;
this file says why.

## D1 — The fetch guard decides on bytes

**Decision.** `isPrivateOrReservedIp` (`packages/engine/src/ssrf-guard.ts`) reads an address into its 4 or 16
bytes once (`parseAddress`, `packages/engine/src/address-ranges.ts`) and decides from one table, one row per
range with its RFC. The owner signed this off under OPERATING-RULES §5, for strengthening only. The callers, the
exported names and every error message are unchanged. The worker classifies those messages
(`packages/worker/src/fetch/fetcher.ts`) and holds no copy of the rule.

**What it refuses.** IPv4: the 14 rows in `ADDRESS_RANGES`. Limited broadcast `255.255.255.255` falls in
`240.0.0.0/4`. IPv6: the documentation and benchmarking rows, and everything outside the global-unicast block
`2000::/3`. For each prefix that carries an IPv4 address (`::ffff:0:0/96`, `::ffff:0:0:0/96`, `64:ff9b::/96`,
`::/96`, `2002::/16`, Teredo `2001::/32` with its inverted client), it reads that address and applies the IPv4
rule. An address with a zone is refused. Text that Node's `net.isIP` or the parser does not read as an address is
refused too.

**Acting-on answers.**

- Q2: one row for everything outside `2000::/3`. The old guard refused `fc::1` and `fc1::` by reading the first
  byte from the text, so a byte table with only the named ranges would have let them through.
- Q3: `64:ff9b:1::/48` is refused whole.
- Q4: an address with a zone is refused.
- Q10: both readers are kept, because each is redundant with the other only over the text they both accept.

**How it is held.**

- `address-ranges.test.ts`, `ssrf-guard.ranges.test.ts`: one named test per row, inside and just outside each
  prefix. A row that carries an IPv4 address is tested with a private and a public address.
- `ssrf-guard.property.test.ts`, no regression: the old function, kept only in that file, against the new one.
- The same file, independent truth: a verdict computed from generated bytes with masks written apart from the
  table, checked against several spellings of each byte string.
- The tests above run with
  `pnpm --filter @crawlmouse/engine exec vitest run src/ssrf-guard src/address-ranges`.
- Mutations, run by hand with `cp` backups and recorded in the step's notes: dropping any row, widening
  or narrowing an embedding prefix, swapping the Teredo halves, or shifting the 6to4 offset each
  turned a named test red.

**Known gaps** (follow-ups): an IPv6 literal in a URL keeps its brackets and fails as a DNS failure, which is
refused but classed `dns_failed`. The rest of `2001::/23` and ORCHID `2001:10::/28` pass, as they did before.

## D2 — A pure app shell is found and said; the grade population does not change

**Decision.** A route that serves an empty root is classed `thin` and is not graded. It is now an
_empty-root page_: a crawled page that answered 200 with HTML, was classed `thin`, and whose crawl row
v1's JS detector read as an app shell (`content_features.client_rendered`). The rule is one predicate,
`emptyRoot` (`packages/engine/src/v2/render/empty-root.ts`). The detector reads it through
`emptyRootUrls`; the render and `buildCheck`'s render guard read the empty-root phase's picks,
`selectEmptyRoots` over the same crawl (`plannedEmptyRoots`, `packages/engine/src/v2/build/plan.ts`).

- The render runs in two phases (`render/run.ts`). The graded phase is the render as it was. Once it has
  settled, the empty-root phase renders up to `EMPTY_ROOT_MAX_RENDERS` pages, `EMPTY_ROOT_PER_TEMPLATE`
  a template, under its own allowance, daily reservation and stop. They are drawn from every crawled
  page, but only from templates with no graded page: the detector judges a template with a graded page
  on its graded renders alone, so a render there would decide nothing (R2-B1). They are ordered by
  template key, then PageRank, then URL. `docs/specs/v2/14-render.md` gives the numbers.
- The detector counts a template _present_ when it has a graded page or an empty-root page. A
  template with a graded page is judged on its rendered graded pages alone, so its verdict and
  confidence are what they were before CC-32; with no graded page rendered it reads `not_rendered`,
  whatever its empty-root pages show. Only a template with no graded page is judged on its rendered
  empty-root pages. `renderedConfidence` counts the renders that decided the verdict.
- `buildCheck` admits a render of a sampled page the graded phase may render, or of one of the
  empty-root picks `selectEmptyRoots` makes from the same crawl, and refuses any other.
- A throw out of an empty-root page leaves that phase's pages `phase_threw`; the graded phase stands.
  When today's budget refused the graded phase or threw, the empty-root phase does not ask it.
- No grade input moves. Verify:
  `pnpm --filter @crawlmouse/engine exec vitest run src/v2/build/no-grade-moves.test.ts src/v2/render/run.empty-root.test.ts`.
  The first builds each build fixture and each grade-guard case with the empty-root phase at 0 and at
  `EMPTY_ROOT_MAX_RENDERS`, with room for both phases and under a per-day cap the graded phase fills,
  and compares every grade, component, content, signals, coverage and site text-share number.
- The fixture `packages/engine/fixtures/v2/build/empty-shell-site.ts` is an empty shell on every route
  but one; its expected records are written by hand in `src/v2/build/empty-shell-site.test.ts`.

**Acting on.**

- _Q6, corrected._ The empty-root phase comes last: its allowance is the per-check browser time the
  graded phase left, not render slots. So it renders on a large site too, whenever the graded renders
  leave time; Q6's premise that a site with 25 or more graded pages renders no empty-root page was
  wrong. Its renders decide only templates with no graded page, so they cannot move a graded
  template's verdict. Where the graded phase uses the time, a template of empty-root pages alone reads
  `not_rendered`. Owner ruling: changing which pages Readable reads is a §5 question for later.
- _Q8, as ruled._ A template of empty-root pages alone has no graded page, so its fix's estimated effect
  is 0. Such a fix now ranks first among the site's fixes (`shellOnly`, `grade/effects.ts`, ties by
  fingerprint); its counterfactual changes no graded page, so no other fix's effect, absorption or the
  overview moves. The views head a `client_rendered_template` fix whose AI effect is not above 0
  (estimated at 0 or less, or not yet estimated) with "Makes N pages readable without JavaScript"
  (`pages_readable`, `apps/web/lib/v2/view/effect-headline.ts`), never a grade number, never "no
  measurable effect" and never why the AI effect waits. N is the fix's `affected_pages`: for such a
  template, its crawled empty-root pages, which is what the check saw. How many of them were rendered
  is not on the Fix record, so no sample size is printed. A fix the last check did not detect keeps
  its count from that detection, so its line reads "Would make N pages readable without JavaScript,
  as of the last check that detected it". In a group row, such a fix is counted in the pages part and
  not as an AI effect that waits.
- _A known difference from the ruling's letter, for the owner._ The view cannot see whether a
  template has graded pages (the Fix does not carry it), so its line also fires on a
  `client_rendered_template` fix whose template has graded pages, when that fix's AI effect is not
  above 0: estimated at 0, or waiting. An estimate reaches 0 only by rounding: its counterfactual sets
  each graded page's share to 1, the most a share can be. An effect that waits is a grade that waits;
  the pages the fix counts do not depend on it. In both cases the line is still true. It is not ranked first; the engine's rule is
  the template with no graded page. The ruling keeps D4's wording for every other fix. Verify:
  `pnpm --filter @crawlmouse/engine exec vitest run src/v2/grade/effects.rendered.test.ts src/v2/build/empty-shell-site.test.ts`
  and `pnpm --filter @crawlmouse/web exec vitest run lib/v2/view/pages-readable.test.ts`.

**Known gaps.**

- **The coverage count is not stored.** The brief asked for `Check.coverage.empty_root_pages`. The
  contract forbids an optional key (`packages/types/src/v2/contract.test.ts`, "no field anywhere in the
  contract is optional"), and a required or nullable key would fail every stored check, so it was
  stopped for the owner. The count is computable from the stored rows today (`emptyRootUrls`).
- **Across checks.** The empty-root phase spends per-check time the graded phase left, under the
  unchanged per-check and per-day caps, so a day's total can be reached sooner and a later check's
  graded phase refused `daily_cap`. Within one check no grade input moves; across checks this is the
  one way the phase can, bounded by `EMPTY_ROOT_MAX_RENDERS` renders a check.
- A check can now make up to 30 renders, 25 graded and 5 empty-root, under the unchanged browser-time
  caps. The render step still has no deadline of its own, and the empty-root phase can lengthen it by
  up to about 225 s, so the deadline it needs before production renders are switched on has to cover
  both phases.
- A page left `phase_threw` records no detail of the error.
- `renderCheck` trusts its caller to pass every crawled page as `emptyRootCandidates`, as
  `renderCandidates` does: a caller that passed empty-root pages alone would get picks in templates
  with a graded page. It is not refused, because no check on the pool tells that misuse from a real
  crawl in which every page fetched is an empty-root page: the homepage, the one page classed content
  whatever its text, is not among the pages when its own fetch failed or robots.txt kept us from it.
- An open fix's shell template is not put first in the empty-root phase; the order is by key alone.
- The built-site recording (`fixtures/v2/build/generate.ts`) leaves the empty-root phase off, so the web
  fixture built from it is unchanged; `empty-shell-site.ts` carries the phase.
- Production renders nothing until a daily budget is set (`apps/web/lib/v2/pipeline/steps/finish.ts`), so
  each crawled shell template's record reads `not_rendered` there, and the check that first detects it
  writes no `opened` change row (`diff/diff.ts` `measuredBefore`).

## D3 — A fix whose subject is gone is measured, as `template_absent`

**Decision.** `detectRendered` gives a record to each template an awaiting client-rendered fix names
(`awaitingShellTemplates`, `AWAITING_FIX_STATUSES`), the helper the render planner reads too. When the
check holds no graded and no empty-root page of the template, the record is `indeterminate`, reason
`template_absent` (appended to `RENDERED_INDETERMINATE_REASONS`, engine-local). The lifecycle's rule
for an indeterminate record applies; no state is added. Verify:
`pnpm --filter @crawlmouse/engine exec vitest run src/v2/detectors/rendered-absent.property.test.ts`, a
fast-check property over generated pages and fixes through `detectorOutcomes` and `diffCheck`: each
awaiting fix with a template key gets a record, and the diff moves its last measurement to the check.

**Acting on.** F3 is reframed, not closed: an open fix whose template is gone is measured again on each
check and reads indeterminate; a fix marked done becomes `unable_to_verify`. The fix does not close by
itself.

**Known gaps.** A template that comes back is measured as usual; one that never does keeps its open fix
open, now measured. `template_absent` is not stored: the fix keeps `last_state` `indeterminate`, and its
`gone` field holds a page's 404 or 410 only, which cannot say "template gone" without a contract change,
so the dashboard cannot tell a gone template from one not rendered. An awaiting fix whose
`template_key` is null cannot be named by template: it gets no record and stays as it was (the
property generates that case). The detector opens every fix with its template's key.

## D4 — An effect at or below zero is shown as no measurable effect

**Decision.** The engine keeps the number it computed. In `apps/web/lib/v2/view/effect-headline.ts`,
`formatPoints` is the one printer of an effect's sign: a figure above zero only. The headline is, in
order: AI points above 0; for a `client_rendered_template` fix whose AI effect is not above 0, the
pages it makes readable (D2's Q8 ruling); waiting where it waited before (and, for a structure fix,
when its Technical SEO effect is at or below 0 and its AI effect is not estimated); Technical SEO
points above 0; "SEO not estimated" when that effect is null; otherwise `no_effect`, "No measurable
effect on the grade" (short form "No measurable effect"). A group's points take each member at 0 first
(`groupSum`). D4 leaves the fix order unchanged. Verify:
`pnpm --filter @crawlmouse/web exec vitest run lib/v2/view/effect-points.test.ts lib/v2/view/plus-sign-guard.test.ts`.
The guard fails on a line under `lib/v2/view` that holds `+${` or a quoted plus sign and is not an
allowlisted line of its file; its self-test shows it flags a mid-template `+${` and a second such line
in an allowlisted file.

**Acting on.** _Q5:_ the printers are `points`, `fixFirstBody`, `restPoints` (the "N more" row) in
`result.ts`, and `effectOf`, `proPoints` and `groupPoints` in `segment/fixes.ts`.

**Known gaps.** A minted report snapshot keeps the text it was minted with. Screens whose fixtures print
a group of zero effects now read "No measurable effect" where they read "+0 …"; their visual baselines
were not re-taken here.

## D5 — The worker records front-end markers

`StackSignals.frontend_markers` is new and optional: a list from the closed `FrontendMarker` enum, each marker
once, in enum order. The worker's reader sets it on the batch's first page. It reads the markers from markup and
response headers it already holds, with no extra request, and stores nothing but enum values. A row without the
field was written before the worker recorded it. An empty list is a read that found none. `stackOf`
(`build/record.ts`) sets `stack.frontend` to Hydrogen, else Next.js, else Shopify Liquid. The packet's first body
follows (`frameworkOf`). Q1: the field was not in the contract, as the brief said. It was proposed only, so it was
added, additively.

**Deploy order.** The worker batch schema is strict, so the web app must know the field before the worker
writes it. The web app deploys on merge, and the worker deploy comes after. Rolling the web app back past this
merge, once the worker writes the field, fails every check that holds such rows (`steps/stored.ts` re-parses
stored batches).

## D6 — `js_only_navigation` can open

**Decision.** The render step reads the same-site link targets of both sides of each page it measures, with one
extractor (`packages/engine/src/v2/render/links.ts`): the crawl's own `extractPage` with non-content links left
out, each target in `canonicalizeUrl`'s spelling, kept when it is on the page's site by the planner's rule
(`inSiteScope`), is not the page itself and is within the URL bound. A side keeps the longest prefix of its
sorted targets that holds at most `MAX_RENDER_LINKS` (200) targets and `MAX_RENDER_LINK_CHARS` (32 KiB) of URL
characters; a side that leaves a target out, or has a target past the URL bound, marks the page `truncated`, and
the detector reads no truncated page. The lists sit
on the engine's `RenderOutcome` page as `links`, which the pipeline stores as evidence. They are not written to
`PageResult.without_js`: the `page_results_without_js` CHECK allows four keys, and a test pins them. No contract
field and no migration was needed.

The detector (`detectors/js-only-navigation.ts`) reuses `client_rendered_template`'s population, deciding pages,
verdict and `template_absent` rule. A deciding page is evidence when it was measured and carries `links` with no
side truncated; its JS-only targets are its rendered targets less its static ones. The record keeps each evidence
page's count and its first `MAX_JS_ONLY_TARGETS` targets. The fix's counterfactual (`grade/effects.ts`
`linkedInHtml`) adds each kept target as a static link from its page through `addEdge`, only for targets the crawl
holds as pages, so anchor diversity leaves those links out. `COVERAGE_DEPENDENCE.js_only_navigation` is `sample`,
and the type is in `DETECTORS_RUN`. The generated specs 14, 17, 19, 20a and 30 say the rest.

Tests: `pnpm --filter @crawlmouse/engine exec vitest run src/v2/render/links.test.ts src/v2/render/run-links.test.ts src/v2/detectors/js-only-navigation.test.ts src/v2/grade/effects.js-only.test.ts src/v2/build/js-nav-site.test.ts`.

**Acting-on answers.**

- Q7: the fix opens from measured evidence, with no packet, no effort and no before and after. The packet's
  registry reason no longer says the render keeps no link. Writing the packet body is a later step.
- Plan review B6: the comparison is the render's own two sides, not the crawl's edges, which are capped at
  1000 a page while `links_read` can still be true.
- Plan review R3: `links` lives on the render outcome only.

**What changes on a built check.** Every present template gets a `js_only_navigation` record. On the recorded
build fixture, `expected.json` gains `js_only_navigation` in `diff_inputs.detectors` and one indeterminate
fingerprint, `jsnav:/guides/{slug}`: that template's pages were not rendered, so it reads `not_rendered`, as its
`client_rendered_template` record does. Its other templates read `not_detected`. `render.json` was re-recorded
with `fixtures/v2/build/generate.ts`: each rendered page gains `links`, and nothing else in it changed. The
grade guard's `expected.json` changed its source digest only; its cases are unchanged, and
`fixtures/v2/grade/write-expected.ts` refuses to write changed cases under the same grade version.

**Known gaps.**

- Production renders nothing today (no daily budget), so the type opens on no live check until renders run, and
  every record reads `not_rendered`. As with D2, the first `detected` then writes no `opened` change row.
- The render planner does not put an open `js_only_navigation` fix's template first, as it does for
  `client_rendered_template`. Doing so would change which graded pages are rendered, and so Readable.
- The counterfactual links only from the evidence pages, and only the kept targets.
- An effect computed after higher-ranked fixes can be 0 or less; D4 prints that as no measurable effect.
- The stored render outcome grows, by at most 64 KiB of URL characters a rendered page (2 sides × 32 KiB). On the
  Free cap of 25 graded and 5 empty-root renders that is at most 1,920 KiB a check (30 × 64 KiB), against
  800 KiB a page (2 × 200 × 2,048 characters) and about 23 MiB a check before the character budget. A canonical
  URL is ASCII, so characters are bytes, before JSON quoting. The graded cap is the caller's (`maxRenders`), so
  a larger cap adds 64 KiB a render. The evidence store gzips the file. The figures are rendered in spec 14 from
  the constants.
- The readings stay with the crawl's link rules: a link that is not an `<a href>` (a click handler on a `div`) is
  not a link on either side.
