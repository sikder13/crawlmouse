## What counts as v1

The finders in `apps/web/__tests__/v1-inventory-source.ts` list, from the tree:

- every `page.*`, Next metadata or special file (`layout`, `opengraph-image`, `icon`, `apple-icon`,
  `not-found`, `global-error`, `sitemap` and the rest of Next's conventions) and `route.*` under
  `apps/web/app`, except under a `(v2-preview)` or `(account)` route group at any depth, and except a
  file that is a 404 whenever a v2 flag is off: it imports a `…Enabled` reader from a `…/flags` module
  and every handler it exports opens a top-level `if (!reader()) return …` with a 404 (`api/checks/[id]/claim` today; CC-03's new billing
  routes once merged, which then join the test's pinned list of what the rule hides). A v1 route with a
  v2 branch (`api/auth/magic-link`, `login/verify`) is not a 404 with the flag off, so it stays listed. The rule
  reads a 404 as `notFound()`, a `status: 404` property, or a call whose first argument is 404, so it
  cannot tell `legacy(404)` from `refuse(404, …)`; the pinned list is what catches such a file;
- every `createFunction` call in the `inngest` package: one written as a top-level
  `export const x = inngest.createFunction(…)` is a v1 function, with the cron in its trigger, and the list the serve
  route registers with the pipeline flag off (`inngestFunctions({})`, run, not read) is checked against them; one inside a function body that is not run where it is
  written is a factory's, which is how CC-20b and CC-03 build theirs behind their
  flags, so it is not listed; any other shape makes the finder throw;
- every table created by a migration whose file name is a timestamp followed by `_v2_` is v2; every
  other migration's tables are listed (so `…_engine_v2_crawl_health.sql`, which is v1's, is read).

Not inventoried, and so not ruled here: the middleware (`apps/web/middleware.ts`: the `/r/` and
`/embed/` `X-Robots-Tag`, the consent cookie, CC-SEC's `guardApi`), `next.config.mjs` redirects and the
`/ingest/*` rewrites to PostHog, and the `report-logos` storage bucket (finding B-F8). Their effects
show up through the items that use them (A-7, B-F8).

`/`, `/dashboard` and `/audit/[id]` keep their URLs. A `retire` entry stays while its v1 file is on
disk; the cutover change that replaces the file in place removes the entry in the same commit, and the
inventory test then holds the new file to whatever rule applies to it.

## What was not checked, and why

- **Content of the database-backed pages** (`/r/[slug]`, `/verify/[id]`, `/dashboard`, `/audit/[id]`,
  `/compare/[a]/[b]`) with real rows: the production build runs on the placeholder values of
  `apps/web/.env.ci`, so D7 exercises only their designed no-data responses.
- **Production environment values** (`INNGEST_SIGNING_KEY` present, `INNGEST_DEV` absent,
  `STRIPE_RECONCILE_LIVEMODE`, `INNGEST_AUDIT_CONCURRENCY`, `CRAWL_PAUSED`): the Vercel API returned 403.
  `vercel env ls production` lists the names.
- **Traffic for D3**: see the query above. `/api/trpc` needs Vercel runtime logs, not PostHog.
- **C-1 end to end** through `runCrawl` and on the deployed function: reproduced against got-scraping
  with the crawler's own `dnsLookup` option; a crawl-path run is CC-SEC-2's, with its live smoke.
- **Hosted Supabase auth settings** (password grant, leaked-password protection): no tool here reads
  them; the local `infra/supabase/config.toml` does not prove the hosted value.
- **PostHog and Sentry retention**, and the privacy page's error-only session-replay statement: not in
  the database.
- **Inngest account-wide concurrency** once CC-20b's functions share the Free plan's slots: dashboard only.
- `lib/billing/csv`, `lib/origin`, `lib/logo-validation` and `lib/auth/landing` were read only as far as
  the D4 rows cite them.
