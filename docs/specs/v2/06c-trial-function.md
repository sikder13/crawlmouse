## The trial function

`start_trial_with_ledger(p_account_id uuid, p_hashes jsonb, p_transition jsonb) returns jsonb` is the first-login hook's one database call (`apps/web/lib/auth/first-login.ts`). In one transaction it:

1. refuses to run outside READ COMMITTED (`0A000`; READ UNCOMMITTED, which Postgres runs as READ COMMITTED, is accepted): the ledger is read in a statement after the locks, and READ COMMITTED gives that statement a snapshot taken after them;
2. validates the input, before any lock: anything malformed raises `22023`;
3. locks the account `for update` (a missing or deleted account raises `P0002`);
4. returns `{"outcome": "not_eligible", "hits": []}` unless the account is Free with `trial_used_at` null;
5. takes one transaction-scoped advisory lock per hash (`trial_ledger_lock`);
6. reads the ledger rule (`trial_ledger_refusals`, at `now()`), and returns `{"outcome": "refused", "hits": [...]}` with the kinds that refused, in the order `email`, `device`, `ip24`, writing nothing;
7. otherwise calls `public.apply_entitlement_transition` with `p_transition`'s values, inserts one `trial_ledger` row per hash with `account_id` and `trial_kind = 'pro'`, and returns `{"outcome": "started", "hits": []}`.

A stale `p_expected_version` raises `40001` from `apply_entitlement_transition`. Any error aborts the whole call, so a trial and its rows are written together or not at all (`pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-006c-trial-function.test.ts -t "atomicity"`).

**`p_hashes`** is an array of 1 to 3 objects, each with the keys `kind` and `value_hash` and no other; `kind` is one of `email`, `device`, `ip24`, one row per kind, an `email` row required; `value_hash` is 64 lowercase hex. The hook computes them with `hashLedgerValue` (HMAC-SHA256 under `TRIAL_LEDGER_PEPPER`); the pepper stays in the app.

**`p_transition`** is what the hook computes with `next()` for `trial_started {variant: 'no_card'}` and `toTransitionParams`, plus `"event": "trial_started"`: the 16 arguments of `apply_entitlement_transition` and the event. The function requires the event, this account's id, `p_state = 'pro_trial'`, `p_tier = 'pro'`, `p_trial_variant = 'no_card'`, a trial end, a trial-used date and `p_at` written as ISO 8601 with an offset (no `infinity`, `epoch` or `now`), the trial end after `p_at`, integer version and limits, and `p_subscription_id`, `p_past_due_tier`, `p_past_due_since` and `p_disputed_at` null. It checks the shape and copies none of the state machine: the limits and dates are `next()`'s. Each rejected shape: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-006c-trial-function.test.ts -t "input validation"`.

**Lock timeout (`TRIAL_LOCK_TIMEOUT`): 3s**, set on the function (`set lock_timeout`), so a stuck account row or hash lock ends the call with `55P03` rather than hanging a sign-in.

### The ledger rule

`trial_ledger_refusals(p_hashes, p_now)` is the rule's one implementation. A trial is refused when `trial_ledger` holds, under the same kind and hash:

- `email`: a row created after `p_now` less 12 calendar months, counted in UTC (Postgres clamps 29 February to 28 February);
- `device`: 2 or more rows created after `p_now` less 720 hours (30 days of 24 hours, so a session time zone with a DST change does not move it);
- `ip24`: 2 or more rows in that window, and a row of the device hash sent in the same window. With no device hash sent, the network refuses nothing.

A row exactly at a window's start is outside it; a row dated after `p_now` is inside. Rows of other kinds (CC-04's `hostname` and `card_fingerprint`) are not read. The numbers are the ones `apps/web/lib/auth/ledger.ts` names for spec 25, and vectors built from them run through the SQL. A pepper shorter than 32 characters reads as none: the hook then calls nothing. Verify the edges by hand-written vectors and a property over generated ledgers: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-006c-trial-function.test.ts -t "the ledger rule"`.

### Locks and concurrency

The function locks the caller's account row first, then the hash keys in ascending order. A hash's key is its first 32 bits under the class 1728 (0x06C0), in the two-key form, which shares no key with the one-key lock `scripts/db` takes. Two calls sharing hashes take the shared keys in the same order, and neither holds the other's account row unless both are for one account, when the second waits on that row before taking any key; so no cycle of waits forms between two calls (the races below run both shapes). Two hashes that share a key only wait for each other.

PGlite has one backend, so its tests show the locks held (one advisory lock per hash, and the account row's `xmax` set, which any row lock does) and taken in ascending order, and each race's sequential outcome. Two real transactions are `pnpm --filter @crawlmouse/scripts exec vitest run db/trial-race.test.ts`: on one device hash the second waits, then is refused; on one account the second waits, then is `not_eligible`; each ends with one trial and the right rows; and while a call that refuses is open, a third session's `FOR KEY SHARE NOWAIT` on the account fails, which only `FOR UPDATE` (or stronger) gives. The file also builds a database from this migration with the advisory-lock call removed, where the device race must start two trials, and one with `for update` weakened to `for key share`, where that third session must get in: it shows it can fail on every run of the file, which CI's `db-cli-files` job makes with `TRIAL_RACE_REQUIRED=1` and `--passWithNoTests=false`.

## What the hook does with the answer

| Outcome        | Meaning                                                                                                                            |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `started`      | the no-card Pro trial started; three ledger rows, or fewer when the device or IP is unknown or the device is not sent              |
| `denied`       | a ledger row refused it; the account stays Free                                                                                    |
| `not_first`    | not the verify that confirmed the email, or another run won the version check                                                      |
| `not_eligible` | the account is not Free, or has used its trial, or the state machine gives it none                                                 |
| `failed`       | the trial function errored, timed out on a lock, or answered something unreadable: Free, `auth.trial-decision-failed`, not retried |
| `no_account`   | the user has no v2 account (from before migration 001): nothing is done                                                            |
| `no_pepper`    | TRIAL_LEDGER_PEPPER is missing or short: no ledger read or write, Free, a Sentry signal                                            |

A call that fails is reported to Sentry as `auth.trial-decision-failed` with a `reason`: `lock_timeout` (`55P03`), `malformed_result` (an answer that is not `{outcome, hits}`), or `rpc_error` with its SQLSTATE in `code` (a revoked grant is `42501`, a missing function `PGRST202`). `40001` is a lost race, read as `not_first` and not reported. ## Apply path

1. The pull request's DB dry run (`db-dry-run.yml`, `docs/ops/db-migrations.md` §1) applies the file to a branch made from production, runs it again, runs the checks, and runs the revert.
2. Merge. The code reaches Vercel at once; with `V2_ACCOUNT_DOOR` unset in Production the first-login hook does not run there.
3. The owner approves the `production` environment and `db-apply-prod.yml` applies the file.
4. **After the apply**, the owner verifies: `pnpm --filter @crawlmouse/scripts exec tsx db/check.ts --project-ref ezspnfeyzwsisymytssm --yes-production` passes, and the read-only query `select proname, prosecdef, proconfig from pg_proc where proname in ('start_trial_with_ledger', 'trial_ledger_lock', 'trial_ledger_refusals')` returns the three rows of the table above. ## Known gaps

- **A failed decision is not retried** (D11). First login is detected once (`isFirstLogin`); a sign-up whose call failed stays Free, and Sentry has `auth.trial-decision-failed`.
- **The 3s lock timeout can cost a trial.** A first login that waits longer than that, for instance on a busy shared network's `ip24` lock, fails and is not retried.
- **A browser with no `cm_auth_for` sends its device.** A link opened where no door request was made (another device, or a browser that never asked) cannot be told apart from someone else's link, so D9 does not apply there.
- **Two clocks.** `next()` dates the trial with the app's clock; the ledger windows and the rows' `created_at` use the database's `now()`.
- **The race test runs only in CI's `db-cli-files` job**; `pnpm test` skips it, because no local Postgres server is assumed. It refuses a `TRIAL_RACE_DB_URL` that is not on this machine.
- **Definer functions outside this migration.** Read from `pg_proc`, those whose `search_path` does not name `pg_temp` last, with the client roles that may call each: none. Migration 20261108000002 (CC-SEC, `docs/specs/v2/sec-baseline.md`) set it last on the rest, and the catalog check `09-definer-search-path.sql` fails on one that does not.
