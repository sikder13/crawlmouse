# CC-33 — operations: the support console, founder notifications, the help centre, in-product support

This step builds the operating side of the product: who staff are, what they may see and do, what the
founder is told, where a customer can read an answer, and how a customer reaches us from inside the
product. It adds no customer feature and changes no grade.

## Decisions

| #   | Decision | Why |
| --- | -------- | --- |
| D1  | **Operators, and accounts marked internal.** A table `operators (user_id, added_at)`, readable and writable by the service role only, filled by `pnpm ops:operator add <email>` (it refuses an address with no user). `accounts.internal boolean not null default false`, hidden from clients by the per-column grants, set only by `pnpm ops:internal <account-id>`. One SQL function, `is_operator()`, answers whether the caller is an operator; it is the only test of it, and no route compares emails or reads an environment list. A server event and a founder notice about an internal account carry `internal: true`. | Staff access and test data are decided in one place, and the repo holds no person's address. |
| D2  | **The support console, read-only, at `/internal`.** For operators only: anyone else, signed in or not, gets 404; the pages are `noindex` and outside the sitemap. Search by email, account id, site host, check id or Stripe customer id. One page per account: plan state and its history, seats, sites, the last 20 checks with status and failure reason, mail sent (from the ledger: kind, status, time, never the body), alerts, open fixes, the Stripe customer id as a dashboard link. Reads use the service role behind the operator check. Two actions, each a POST with a reason, each written to `operator_actions` (who, what, target, reason, when): re-run a failed or reaped check (the existing request path, limits unchanged), and re-send a sign-in link to the address of a user of that account (the per-address limit unchanged). A view of an account is written to `operator_actions` before its data is read. Built from the design system's table, card and field pieces; it is staff tooling, so it has no artboard. | Support answers in minutes, and every look at a customer's data is on record. |
| D3  | **Founder notifications, through the one mailer.** Two kinds, in the account-mail class (no unsubscribe, never suppressed): `founder_event` (instant: sign-up, trial started, first payment, cancellation, agency account created, payment failed) and `founder_digest` (daily at 08:00 America/New_York for the day before; on Monday also the week's totals and the change against the week before). Recipient `FOUNDER_NOTIFY_TO`; unset, nothing is sent and one log line says so. Each instant notice has a ledger key from its event, so a retried webhook cannot send twice. A notice names the plan, the amount as Stripe states it, the account id as an `/internal` link and the site host; it carries no card detail and no address but the account owner's. An internal account's notice has a `[TEST]` subject and is left out of every digest total. The Sentry alerts stay. More than 20 instant notices in an hour become one "N more" notice. | The founder knows about every customer the moment they arrive. |
| D4  | **The help centre at `/help`.** Server-rendered, indexable, in the sitemap while `V2_CHECKS_PUBLIC` is on and 404 while it is off, in the v2 public page shell. Twelve articles, each titled as the reader's question. Prices and limits render from `prices.ts` and `GATES`; a capability `CAPABILITIES` marks coming is described as coming or left out; a test fails on a typed price or limit and on an article naming an unbuilt capability as built. One `<h1>`, a canonical, a title and a description per article; no `FAQPage` markup (owner ruling 2026-11-11). The footer's Help link is one row of the v2 footer's table. | A question with a page is a question support does not answer twice, and each page is search content. |
| D5  | **Support from inside the product.** An "Email support" link in Settings and on each error screen; "Something wrong with this fix?" on the fix page. Each is a `mailto:` to the support address whose subject and first lines carry the ids the page has (account, path, site, check, fix and its type, the error's Sentry event id), never an email address or a crawled string, built by one function with a property test. An error boundary (`error.tsx`) for the account, sites, dashboard, alerts and changes segments renders a v2 error screen: what happened in one sentence, a retry, the support link and the Sentry event id. | The fastest signal of a wrong finding is the customer telling us, with the ids attached. |
| D6  | **The sign-in canary.** Resend's webhook records the delivery of the sign-in mail Supabase Auth sends through SMTP (evidence: questions Q4), so the canary is built: every 10 minutes, registered only when `SIGNIN_CANARY_TO` is set, it requests a sign-in link for that address and raises Sentry `signal:signin-canary` when no delivery is recorded within 5 minutes. `docs/ops/uptime.md` lists the monitors the owner creates; `/status`'s sentence about status.crawlmouse.com is removed. | The launch-day abort signal has to exist, and a canary that cannot see a failure is worse than none. |

## Out of this step

Test accounts for each tier, lifecycle mails, extending a trial from the console, session replay, the
status-page vendor, switching any flag.
