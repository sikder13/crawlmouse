# 20b — The check pipeline (CC-20b)

> Generated by `pnpm --filter @crawlmouse/web exec tsx lib/v2/pipeline/write-spec.ts` from `apps/web/lib/v2/pipeline/spec.ts`. Do not edit by hand: `lib/v2/pipeline/spec.test.ts` fails when this file differs. Decisions and rulings: `~/crawlmouse-plan/notes/cc-20b/` (brief, plan, questions, rulings).

A `check.requested` event becomes a finished, persisted, readable check: `requestCheck` writes the queued row and sends the event; `checkFn` claims it, reads the seeds, crawls and tests access through the Fly worker by polling, renders, builds with `buildCheck`, persists with the one writer, and emits `check.finished`. With `V2_PIPELINE` unset nothing here is registered, and the serve route registers what it registered before (`pnpm --filter @crawlmouse/web exec vitest run lib/v2/pipeline/functions.test.ts`).

## Functions

| Id                           | Trigger                                            | What it does                                                                                                                                      |
| ---------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `crawlmouse.check.run`       | `check.requested`                                  | runs one check (below)                                                                                                                            |
| `crawlmouse.check.cancelled` | `inngest/function.cancelled` of the check function | fails `canceled` the check the cancelled run’s event named, or else the check its run claimed; `onFailure` does not fire on a cancel or a timeout |
| `crawlmouse.check.reaper`    | cron `*/10 * * * *`                                | fails a queued or running check whose heartbeat (or, unclaimed, its queue time) is older than 30 minutes, and releases its posted batches         |

Concurrency: one plan cap, `PLAN_CONCURRENCY_CAP = 5` (Inngest Free), which the registered functions’ limits are clamped to, v1’s audit function included (Q3; `pnpm --filter @crawlmouse/web exec vitest run lib/v2/pipeline/functions.test.ts` sweeps them). The check function’s account-wide limit is `INNGEST_CHECK_CONCURRENCY`, default 2. Its per-site key does not keep two checks of a site apart, because Inngest counts executing steps and a sleeping run holds none; the database does (`checks_one_running_per_site`, Q13).

## The steps of a check

| Step                                         | Reads                                                                                                                                        | Writes                                                                                                           |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `claim`, then `claim-wait-{i}` / `claim-{i}` | `CRAWL_PAUSED`; `claim_check`; the claimed check’s site, host and account from the database (a site other than the event’s fails `internal`) | `checks` queued → running (5 waits of 60 s while the site has a check running)                                   |
| `discover`                                   | robots.txt and the sitemaps, from the app through `safeFetch` (Q8)                                                                           | `seeds.json.gz`                                                                                                  |
| `crawl-{n}-post`                             | seeds and stored batches → `nextCrawlBatch`                                                                                                  | `checks.heartbeat_at`, `progress`; `crawl_batches` (upsert, never over a done batch); the worker’s `POST /batch` |
| `crawl-{n}-wait-{i}`, `crawl-{n}-poll-{i}`   | the worker’s `GET /batch/{id}`                                                                                                               | `checks.heartbeat_at`, `progress`                                                                                |
| `crawl-{n}-read`                             | the result, parsed with `BatchResultSchema`                                                                                                  | `batch-{n}.json.gz`; `crawl_batches` done                                                                        |
| `access-{s}-…`                               | stored batches → `assemble` → `sample` (stage 2 only when needed)                                                                            | as crawl; batch numbers continue the crawl’s                                                                     |
| `render`                                     | `renderCandidates`, the previous check’s page states                                                                                         | `render.json.gz` (Q7: the daily budget refuses)                                                                  |
| `build`                                      | everything above, the previous graded check and its `diff_inputs`, the site’s fixes and events                                               | `built.json.gz`, `map.json.gz` (`checkMap`)                                                                      |
| `persist`                                    | `built.json.gz`                                                                                                                              | staged chunks, then `persist_built_check` in one transaction (Q11)                                               |
| `emit`                                       |                                                                                                                                              | `check.finished`, under the id `check-finished:{check_id}`                                                       |
| `finalize`                                   |                                                                                                                                              | removes `built.json.gz`                                                                                          |

`runCheck` (`inngest/check.ts`) runs each of its steps through `sized`, which throws, naming the step, when an output is 4096 bytes or more as JSON (`pnpm --filter @crawlmouse/inngest exec vitest run check.test.ts` proves it on `discover`); bulk data goes to the private `evidence` bucket, at `{account_id|anon}/{site_id}/{check_id}/{name}.json.gz`.

## Polling and time

| Bound                                                         | Value                   |
| ------------------------------------------------------------- | ----------------------- |
| First poll wait, doubling to                                  | 5 s, 30 s               |
| A batch is lost after its `max_seconds` plus                  | 60 s                    |
| A lost batch (`not_found`) is posted again                    | once                    |
| Wait after the worker answers busy, and busy answers per post | 30 s, 20                |
| The run’s finish timeout                                      | 1200 s                  |
| Crawl phase ceiling                                           | 480 s                   |
| Access stages’ slice                                          | 300 s                   |
| Reserve for render, build, persist, finalize                  | 180 s                   |
| A batch that would get less is not posted                     | 60 s                    |
| Discovery                                                     | 60 s, 5000 sitemap URLs |
| Crawl batches per check                                       | 40                      |
| Default page cap                                              | 500                     |

| Batch budget | Requests | Bytes   | Seconds (cut to the time left) |
| ------------ | -------- | ------- | ------------------------------ |
| crawl        | 400      | 128 MiB | 240                            |
| access       | 500      | 128 MiB | 240                            |

The worst case these allow fits the finish timeout, and the worst-case step count fits Inngest’s per-run limit: `pnpm --filter @crawlmouse/web exec vitest run lib/v2/pipeline/steps/time.test.ts`.

## Failure reasons

`checks.failure_reason` is readable by the site’s members, so the pipeline writes one of these words. Its stores refuse a word outside the list, and so do `fail_check` and `reap_stalled_checks`, which read it from `check_failure_reasons()`, a SQL function a test holds equal to the list (`pnpm --filter @crawlmouse/web exec vitest run lib/v2/pipeline/store.test.ts __tests__/v2-008-pipeline.test.ts`).

| Reason               | When                                                                                |
| -------------------- | ----------------------------------------------------------------------------------- |
| `paused`             | `CRAWL_PAUSED=1` when the check was claimed, or the worker answered `paused`        |
| `site_busy`          | another check of the site was still running after the claim waited                  |
| `canceled`           | the run was cancelled or passed its finish timeout (Inngest reports both alike)     |
| `stalled`            | the reaper found a claimed check with no heartbeat within its bound                 |
| `not_started`        | the reaper found a check that no run claimed within its bound                       |
| `worker_redeployed`  | a batch came from another worker release than the check’s first (Q10)               |
| `worker_unavailable` | no crawl batch could be posted or read, or the worker refused the app’s credentials |
| `build_failed`       | `buildCheck` threw                                                                  |
| `persist_failed`     | persisting the built check threw                                                    |
| `internal`           | anything else                                                                       |

## Requests

| Trigger                                      | Idempotency key (the event id and the source of the check id) |
| -------------------------------------------- | ------------------------------------------------------------- |
| `manual`                                     | `check:{site}:manual:{bucket}`, a 120-second bucket           |
| `fix_recheck`                                | `check:{site}:recheck:{bucket}`, the same bucket              |
| `scheduled`                                  | `check:{site}:scheduled:{next_check_at}`                      |
| `deploy`                                     | `check:{site}:deploy:{bucket}`, a 600-second bucket           |
| `first_audit`, and any site no account keeps | by a fresh check id                                           |

A bucketed key’s check id is the engine’s `stableId` of the key, so two requests in one bucket insert one row and send events of one id, which Inngest keeps once (`pnpm --filter @crawlmouse/web exec vitest run lib/v2/pipeline/request.test.ts`). A site no account keeps gets `expires_at` 24 hours out. No caps are enforced here (CC-26b).

## Migrations

- `20261108000003_v2_006d_contract_columns.sql` (Q1): the contract fields SPEC 06 left to CC-06d, so a built check can be stored and read back whole.

## Differences from ARCH-2 §4

- **Polling, not `check.batch.done` (D1).** The deployed worker holds no Inngest or database key and is polled; `step.sleep` holds no Vercel function open.
- **Concurrency default 2, not 20 (D3).** The limits are clamped to the plan cap (above); a higher one makes Inngest refuse the whole app sync.
- **The database serialises a site’s checks**, not the concurrency key (above).
- **Cancel and timeout** are caught by a function of their own, since `onFailure` does not see them.
- **Sitemaps are read by the app** (Q8); the worker reads robots.txt for itself and the sitemap’s status only.
- **Persistence is staged** (Q11): the bulk rows go in chunks while the check runs, and one transaction moves them and flips the status.
- **No rendering in production yet** (Q7): the daily budget refuses until a durable one exists.

## Differences from the brief

- **`emit` runs before `finalize`.** D3 listed `finalize` then `emit`; a finalize that failed after the check was written would have left it finished with no `check.finished` (review round 1). A cancel or timeout between `persist` and `emit` still loses the event (follow-up).
- **Migration 006d ships here** (Q1): without CC-06d’s columns a built check could not be stored whole.
- **`loadCheck` returns `provenance: "measured"`** (Q2), not FixtureDataset’s `"fixture"`.
- **`V2_PIPELINE` registers the functions only** (Q6); the account door’s promises about checks moved to `V2_CHECKS_PUBLIC`.
- **Persistence is staged** (Q11), and **008 creates more than D6 listed** (its table, its columns and `persist_built_check`): `persist_chunks`, `checks_one_running_per_site` and `checks_heartbeat_idx`, and `check_failure_reasons`, `claim_check`, `fail_check`, `reap_stalled_checks`, `stage_check_rows` (Q11, Q13, review round 1).
- **v1’s audit function clamps its concurrency to the plan cap**, not 100 (Q3).
