## How access works

- RLS is on for each table 003 creates, and each starts with `revoke all … from public, anon, authenticated`: production's default privileges would otherwise give `anon` every privilege on a new table, TRUNCATE included. Verify: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-003-check-tables.test.ts -t "posture"`.
- `authenticated` reads site data through `is_member_for_site(site_id)`, directly or through the row's check, and account data (`api_keys`, `seat_sites`) through `is_member()` / `member_role()`. SELECT is granted per column. Verify: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-003-cross-account.test.ts`.
- **Client scope.** `is_member_for_site` is true when the caller has an active seat on the site's live (not soft-deleted) account and that seat covers the site. A seat covers a site when `seats.client_scope_all` is true (the contract's `client_scope: 'all'`; the default, so the seats 001 created keep full access) or when `seat_sites` pairs the seat with the site or with the production site it stages. An owner seat cannot be scoped (`seats_owner_unscoped`).
- `site_fixes` (the packet is Pro content), `fix_events` and `share_links` have no client grant: reading `site_fixes.packet` as `authenticated` is a permission error, not an empty result. Verify: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-003-cross-account.test.ts -t "packet"`.
- `alert_rules` is the one client-written table: a site rule by the seats that cover the site, an account-wide rule by the owner. The trigger `alert_rules_entitlement_check` refuses a write that adds Slack while the account's effective tier is Free; it runs after the row's RLS check and for the service role too. Verify: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-003-check-tables.test.ts -t "alert_rules"`.
- An anonymous site (`account_id is null`) is not readable through RLS (`is_member_for_site` joins the site's account); `/audit/[id]` reads it with the service role, as v1 does. Verify: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-003-cross-account.test.ts -t "anonymous sites"`.

## The `crawl_worker` token

The Fly worker is meant to reach Supabase with this token and nothing else. It never holds the project's JWT signing key: whoever holds a signing key can mint a `service_role` token too.

- **Who mints it.** The server, in the Inngest step that posts a batch to the worker, one token per check (or per batch). It is signed with a project JWT signing key the server holds: the legacy JWT secret, or a key imported into the project's JWT signing keys (Supabase supports importing a private key or setting a shared secret for this). That key is server-side, at the same tier as the service-role key.
- **Claims.** `role: "crawl_worker"`, `check_id` (a lowercase uuid), `iat` and `exp` as numbers, `exp − iat` at most 900 seconds. No `sub`: the token is not a user.
- **What the database checks.** `crawl_worker_check_id()` reads the verified claims (`auth.jwt()`) and returns the check only when the role claim is `crawl_worker`, `check_id` is a well-formed uuid naming a check in status `running`, `exp` has not passed, `iat` is at most 60 seconds ahead of the database clock, and the lifetime is at most 900 seconds. Both policies hold only for that check, so a token minted with a longer life, for another check, or for a finished one is refused by the database, not only by the minter. Verify: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-007-storage.test.ts`.
- **What it may do.** Insert `page_results` rows for its check, without RETURNING (`Prefer: return=minimal`), and upload `evidence` parts under `{account_id | anon}/{site_id}/{check_id}.part{n}.json.gz`. It cannot read, update or delete either, and holds no grant on `frontier` until `frontier.audit_id` stops being NOT NULL. A leaked token can still write any number of rows and parts for its check within its 15 minutes; nothing in the database caps volume.
- **For the step that wires the worker.** Whether the server can mint today depends on the project's key setup, which this step does not read. If the project signs only with Supabase-managed asymmetric keys, the server has no private key to sign with, and a key must be imported (or a shared secret set) before the worker can run. That is a blocker for the wiring step, not for these migrations.

## Where this differs from the design documents

The merged contract (`packages/types/src/v2`) wins where it and ARCH-2 disagree; the owner's rulings of 2026-11-02 settle the rest. The contract guard compares the columns and value sets with the contract: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-contract-guard.test.ts`.

- **Columns and enums follow the contract.** `checks.status` is the contract's `CheckStatus` (ARCH-2 has `canceled` and `refused`, the contract has `partial`); `checks.trigger` is `CheckTrigger` (`first_audit`, `fix_recheck`); `grade_version` is a semver string, not a smallint; `sites.host`, not `hostname`; a staging site points at its production site through `staging_of_site_id` (ARCH-2: `kind` and `parent_site_id`), and competitors are `sites.competitor_hosts`, not rows. Fix types and statuses, change kinds and subjects, alert-rule kinds and fields, report kinds and formats, and `page_results.kind` (v1's `PageKind`) are the contract's lists. `link_edges.js_only` replaces ARCH-2's `via`. The contract's `Fix` is the table `site_fixes`, as ARCH-2 §2.1 (not §2.8's `fixes`).
- **Where the contract's objects are stored.** `Site.schedule` is the `schedule_*` columns (weekday ISO 1–7; ARCH-2's `schedule_dow` is 0–6); `Site.client_report` is `report_schedules`, one row per site keyed by `site_id` (ARCH-2: an `id` key, `recipients`, `send_hour`, `reply_to`, `kind`, `enabled` and a `monthly_first_monday` cadence); `Seat.client_scope` is `seats.client_scope_all` with `seat_sites` (created here, not in 001, because it references `sites`); `Site.paused` is generated from `paused_reason`.
- **Access rules ship with the tables (003), not in a later 006.** A table without them would be open to `anon` from the moment it exists.
- **Per-seat client scoping is in the database** (`is_member_for_site`), not only in route handlers: a signed-in user can call PostgREST directly.
- **No client write on `sites`.** ARCH-2 §2.2 rule 3 grants a client update on the schedule columns behind an entitlement trigger; the brief keeps `alert_rules` the only client-written table, so schedule changes go through a route.
- **`checks` has no `account_id`.** ARCH-2 copies it for RLS speed; here a check reaches its account through `sites`, so no copy can drift from the site's. Its listing index is `(site_id, queued_at desc)` (ARCH-2: `finished_at`), because a queued or running check has no `finished_at`. ARCH-2 says a check is immutable once finished; nothing enforces it here (the contract clears `expires_at` when an account keeps a finished check).
- **`page_results` and `link_edges` are keyed by URL hashes** (sha256 of the UTF-8 URL, as `frontier.url_hash`), set by a trigger: the contract identifies them by URL, and a URL can exceed a btree key.
- **The `changes` idempotency index** is `(check_id, kind, subject, "where", ua, fix_id)` with `nulls not distinct`. ARCH-2's `(check_id, kind, subject)` assumed a fine-grained subject (`crawler:claude-searchbot`); the contract's is a category (`ChangeSubject`). The owner approved the key without `fix_id`; review showed two fixes opened in one check can share subject, place and crawler, so `fix_id` is part of it (open question 4).
- **`alert_events`** is unique on `(rule_id, check_id, channel)`: one rule sends on each of its channels. ARCH-2 says `(rule_id, check_id)`.
- **`alert_rules_entitlement_check`** (ARCH-2's name) refuses only a write that adds Slack, and runs after RLS. A rule that already sends to Slack stays updatable after a downgrade, so the owner can switch it off and alertFn can stamp `last_fired_*`; alertFn decides at send time whether the plan still includes Slack.
- **References between check rows are checked.** Composite foreign keys keep a report, rule, schedule, seat pairing and owner seat inside one account, and a check, change, fix or alert event inside one site. Triggers check what a foreign key cannot: a fix event's check and seat (`fix_events_references`), a rule's last-fired check (`alert_rules_fired_check_scope`) and an alert event's rule (`alert_events_rule_scope`). `fix_events.check_id` is deferred, so deleting an account or a site takes its fixes' events in the same statement as its checks; deleting a check an event still cites fails at commit. Verify: `pnpm --filter @crawlmouse/web exec vitest run __tests__/v2-003-check-tables.test.ts -t "deleting"`. The triggers check a row when it is written; a later service-role change to a parent's site or account (a rule's `site_id`, a fix's `site_id`) is not re-checked against rows that already cite it. No client can make such a change: neither column is in a client grant.
- **`share_links`** stores the token's sha256, not the token. **`fix_events`** has no client grant, like `site_fixes`.
- **Pausing keeps the schedule.** A paused site keeps its cadence, weekday and hour and records `paused_reason`; CC-02's planner models the same pause as `schedule = null`. A site checked on deploy keeps that cadence, except that on a move to Free the oldest site, unless the user paused it, takes Free's monthly check, because Free has no deploy hooks (`GATES.free.stagingAndDeployHooks`; open question 2). A site given a timed cadence without a weekday or hour gets its creation weekday, in the account's time zone (UTC when Postgres does not know the zone), at 06:00 (ARCH-2's defaults). Staging sites are not paused or resumed (open question 3).
- **Counts** are `integer` columns, `bigint` for byte counts: the contract's counts are unbounded safe integers, and `integer` caps them at 2,147,483,647. **Text** columns refuse a NUL character, which the contract's strings accept; the engine strips NUL before persisting.
- **`reports.site_id` is required** (the contract); ARCH-2 allows null for an agency-wide export. ARCH-2's `reports.check_id`, `brand_id` and `schedule_id` are not built.
- **`api_keys.scopes`** are ARCH-2's `read:checks`, `read:fixes`, `read:changes`; SECURITY-DESIGN §3.6 says `['read']`.
- **The evidence path** is ARCH-2 §2.10's `{account_id | anon}/{site_id}/{check_id}…`; SECURITY-DESIGN §7.1 shows `account/<id>/site/<id>/check/<id>`.
- **Not built here:** ARCH-2's `sites.root_url`, `etld1`, `verified_at`, `verification_method`, `public_slug`, `schedule_offset_min`, `next_check_at`, `page_cap`, `latest_check_id` / `previous_check_id`, `trial_protected_until`; the `checks` pipeline columns and the J7 token hash. The contract does not name them, and a column added later is hidden from clients until it is granted. ARCH-2 §2.15's tables (`crawl_batches`, `recipient_confirmations` for J10's double opt-in, `integrations` and the rest) are their own steps, as are SECURITY-DESIGN §10 #8's share and portal RPCs and #12's redaction of stored request headers (the writer's job).

-- Refuses UPDATE, DELETE and TRUNCATE whichever role writes (the service role included). Two writes are let through, both made by a
-- foreign-key action and checked here by what they leave behind: the delete of an event whose fix no
-- longer exists, and the clearing of by_seat_id once its seat no longer exists. SECURITY DEFINER, so
-- the cascade a user deletion starts can read site_fixes and seats whatever role started it.
create or replace function public.fix_events_append_only()
returns trigger
language plpgsql
security definer
set search_path = public, pg_catalog
as $$
begin
  if tg_op = 'DELETE' then
    if not exists (select 1 from public.site_fixes f where f.id = old.fix_id) then
      return old;
    end if;
  elsif tg_op = 'UPDATE' then
    if old.by_seat_id is not null and new.by_seat_id is null
       and (new.id, new.fix_id, new.at, new.kind, new.check_id)
           is not distinct from (old.id, old.fix_id, old.at, old.kind, old.check_id)
       and not exists (select 1 from public.seats s where s.id = old.by_seat_id) then
      return new;
    end if;
  end if;
  raise exception 'fix_events is append-only' using errcode = '55000';
end;
$$;

-- Slack is a paid-plan channel (GATES in apps/web/lib/entitlement-v2.ts). A write that adds Slack to
-- a rule (an insert with it, an update that adds it or moves the rule to another account) is refused
-- when the account's effective tier is Free, as effectiveTier() there computes it: a no-card Pro trial
-- is Free from trial_ends_at, and past_due keeps past_due_tier for 168 hours from past_due_since. A
-- rule that already sends to Slack can still be updated after a downgrade, so it can be switched off
-- and alertFn can record when it fired; whether to send is alertFn's decision at send time. The
-- trigger runs AFTER the row's RLS check, so a client learns nothing about an account it cannot
-- write to, and it runs for every writer, the service role included.
create or replace function public.alert_rules_entitlement_check()
returns trigger
language plpgsql
security definer
set search_path = public, pg_catalog
as $$
declare
  v_tier text;
begin
  if 'slack' = any (new.channels)
     and (tg_op = 'INSERT' or not ('slack' = any (old.channels)) or new.account_id <> old.account_id) then
    select case
             when a.state = 'pro_trial' and a.trial_variant = 'no_card'
               then case when now() < a.trial_ends_at then a.tier else 'free' end
             when a.state = 'past_due'
               then case when now() < a.past_due_since + interval '168 hours' then a.past_due_tier else 'free' end
             else a.tier
           end
      into v_tier
      from public.accounts a
     where a.id = new.account_id;
    if v_tier is null or v_tier not in ('pro', 'agency') then
      raise exception 'alert_rules: Slack alerts need a paid plan' using errcode = '23514';
    end if;
  end if;
  return null;
end;
$$;

-- The check a rule last fired on is one of the rule's account's, and of its site for a site rule.
create or replace function public.alert_rules_fired_check_scope()
returns trigger
language plpgsql
security definer
set search_path = public, pg_catalog
as $$
begin
  if new.last_fired_check_id is not null and not exists (
       select 1 from public.checks c join public.sites s on s.id = c.site_id
        where c.id = new.last_fired_check_id and s.account_id = new.account_id
          and (new.site_id is null or c.site_id = new.site_id)) then
    raise exception 'alert_rules: last_fired_check_id must be a check of the rule''s sites'
      using errcode = '23503';
  end if;
  return null;
end;
$$;

-- True when the caller holds an active seat on the site's live account and that seat covers the site:
-- client_scope_all, or a seat_sites row for the site or for the production site it stages.

returns boolean
language sql
stable
security definer
set search_path = public, pg_catalog
as $$
  select exists (
    select 1
      from public.sites st
      join public.accounts a on a.id = st.account_id

  );

-- ─── apply_entitlement_transition: now with the site effects ──────────────────────────────────────
-- 001's body, unchanged up to the seat removal, then the site effects of CC-02's planSites
-- (apps/web/lib/billing/state-machine-sites.ts), decided as applied() decides them
-- (apps/web/lib/billing/state-machine.ts): pause_others on a move to Free from a paid tier;
-- otherwise pause_over_limit when the site limit falls, resume when it rises.
--
-- They apply to the account's primary sites (not staging, not removed), oldest first by created_at
-- to the millisecond (planSites compares Dates), then id; a site the user paused is not changed but
-- keeps its place in that order. A pause records paused_reason and keeps the schedule; a resume
-- clears it. On a move to Free the oldest site, unless the user paused it, takes Free's monthly check,
-- even if it was checked on deploy (Free has no deploy hooks: GATES.free.stagingAndDeployHooks). Otherwise a timed schedule takes the tier's
-- cadence (Free: monthly, paid: weekly) and a site checked on deploy keeps that cadence, which

revoke all on function public.crawl_worker_part_path_ok(text) from public, anon, authenticated, service_role;
grant execute on function public.crawl_worker_check_id() to crawl_worker;
grant execute on function public.crawl_worker_part_path_ok(text) to crawl_worker;

-- ─── page_results: insert only, for the token's check ─────────────────────────────────────────────
-- No SELECT, so the worker inserts without RETURNING (PostgREST `Prefer: return=minimal`).

grant insert on public.page_results to crawl_worker;

drop policy if exists page_results_crawl_worker_insert on public.page_results;
create policy page_results_crawl_worker_insert on public.page_results
  for insert to crawl_worker with check (check_id = public.crawl_worker_check_id());

-- ─── evidence parts: insert only, under the token's check's path ──────────────────────────────────
-- No SELECT, UPDATE or DELETE on storage.objects, so the worker cannot read, overwrite or remove an
-- object, its own parts included. finalize (service role) joins the parts and deletes them.

grant insert on storage.objects to crawl_worker;

drop policy if exists evidence_crawl_worker_part_insert on storage.objects;
create policy evidence_crawl_worker_part_insert on storage.objects
  for insert to crawl_worker
  with check (bucket_id = 'evidence' and public.crawl_worker_part_path_ok(name));
